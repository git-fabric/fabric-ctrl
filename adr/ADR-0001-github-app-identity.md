# ADR-0001: GitHub App as Zero-Trust Identity Layer

**Status:** Accepted  
**Date:** 2026-03-08  
**Author:** ry-ops

---

## Context

`fabric-ctrl` needs authenticated access to every repository in the `git-fabric` org — for webhook reception, security scanning integration, Dependabot triage, and audit log access. The naive approach is a Personal Access Token (PAT) scoped to the org. PATs are a zero-trust anti-pattern:

- Long-lived credentials with no automatic rotation
- Tied to a human identity, not a machine identity
- Broad scope — no per-repo permission granularity
- No cryptographic proof of origin for inbound webhook events
- No way to enforce least-privilege at the installation level

The `git-fabric` org is designed to be consumed by multiple tools (`git-steer`, `cortex`, Claude Desktop). Each of those consumers needs org access. Multiplying PATs multiplies the attack surface.

## Decision

`fabric-ctrl` will authenticate exclusively as a **GitHub App** — never as a user, never via PAT.

The GitHub App (`fabric-security`) is installed on the `git-fabric` org with the minimum permissions required. All Octokit clients in `fabric-ctrl` are derived from **short-lived installation tokens** (~1hr TTL) generated by the App's private key. The private key is the only long-lived secret and never leaves the local machine.

Inbound webhooks are verified via **HMAC-SHA256** signature (`X-Hub-Signature-256`) using timing-safe comparison. Any request without a valid signature is rejected at the middleware layer before any handler logic executes.

## Consequences

**Positive:**
- Machine identity — `fabric-ctrl` acts as the App, not as a person
- Short-lived tokens — installation tokens expire automatically, no rotation burden
- Cryptographic webhook verification — every inbound event is authenticated
- Least-privilege — App permissions are declared in the App manifest and scoped per-installation
- Auditability — all App actions appear in the org audit log under the App's identity
- No PAT sprawl — consumers authenticate via the App, not individual tokens

**Negative:**
- More setup than a PAT — requires App registration, private key management, and installation
- Private key must be kept secure — loss of the `.pem` file is equivalent to losing org access
- Installation ID must be known and configured — one additional env variable

## App Permissions Required

```yaml
# Repository permissions
contents: read
issues: write
pull_requests: write
security_events: read
workflows: read

# Organization permissions
members: read
administration: read

# Account permissions
# (none required)
```

## Webhook Events Required

```yaml
- push
- pull_request
- code_scanning_alert
- secret_scanning_alert
- repository_vulnerability_alert
- dependabot_alert
- member
- organization
- workflow_run
```
