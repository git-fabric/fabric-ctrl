# ADR-0001: GitHub App as Zero-Trust Identity Layer

**Status:** Accepted  
**Date:** 2026-03-08  
**Author:** ry-ops

---

## Context

`fabric-ctrl` needs authenticated access to every repository in the `git-fabric` org — for webhook reception, security scanning integration, Dependabot triage, and audit log access. The naive approach is a Personal Access Token (PAT) scoped to the org. PATs are a zero-trust anti-pattern:

- Long-lived credentials with no automatic rotation
- Tied to a human identity, not a machine identity
- Broad scope — no per-repo permission granularity
- No cryptographic proof of origin for inbound webhook events
- No way to enforce least-privilege at the installation level

The `git-fabric` org is designed to be consumed by multiple tools (`git-steer`, `cortex`, Claude Desktop). Each of those consumers needs org access. Multiplying PATs multiplies the attack surface.

## Decision

`fabric-ctrl` will authenticate exclusively as a **GitHub App** — never as a user, never via PAT.

The GitHub App (`fabric-security`) is installed on the `git-fabric` org with the minimum permissions required. All Octokit clients in `fabric-ctrl` are derived from **short-lived installation tokens** (~1hr TTL) generated by the App's private key. The private key is the only long-lived secret and never leaves the local machine.

Inbound webhooks are verified via **HMAC-SHA256** signature (`X-Hub-Signature-256`) using timing-safe comparison. Any request without a valid signature is rejected at the middleware layer before any handler logic executes.

## Consequences

**Positive:**
- Machine identity — `fabric-ctrl` acts as the App, not as a person
- Short-lived tokens — installation tokens expire automatically, no rotation burden
- Cryptographic webhook verification — every inbound event is authenticated
- Least-privilege — App permissions are declared in the App manifest and scoped per-installation
- Auditability — all App actions appear in the org audit log under the App's identity
- No PAT sprawl — consumers authenticate via the App, not individual tokens

**Negative:**
- More setup than a PAT — requires App registration, private key management, and installation
- Private key must be kept secure — loss of the `.pem` file is equivalent to losing org access
- Installation ID must be known and configured — one additional env variable

## App Permissions Required

```yaml
# Repository permissions
contents: read
issues: write
pull_requests: write
security_events: read
workflows: read

# Organization permissions
members: read
administration: read

# Account permissions
# (none required)
```

## Webhook Events Required

```yaml
- push
- pull_request
- code_scanning_alert
- secret_scanning_alert
- repository_vulnerability_alert
- dependabot_alert
- member
- organization
- workflow_run
```

# ADR-0002: Webhook Server as the Security Event Bus

**Status:** Accepted  
**Date:** 2026-03-08  
**Author:** ry-ops

---

## Context

`fabric-ctrl` needs to react to security events across the org — not poll for them. Polling is slow, burns API rate limits, and creates windows where threats go undetected. The alternative is a push-based webhook receiver that processes events in real time.

## Decision

`fabric-ctrl` runs a lightweight **Hono** webhook server as one of its two entrypoints (the other being the MCP server). All GitHub org events flow through this server. The server is the single inbound surface for the org's security event stream.

The server is intentionally minimal — it receives, verifies, and dispatches. Business logic lives in typed handler modules (`push.ts`, `security-alert.ts`, `dependabot.ts`, `audit.ts`). This separation makes handlers independently testable and replaceable.

## Consequences

- `fabric-ctrl` must be reachable from GitHub's webhook delivery IPs (requires a public endpoint or tunnel in dev — e.g., `ngrok`, Cloudflare Tunnel, or a k3s ingress in prod)
- Webhook delivery failures are retried by GitHub for up to 72hrs — the server must be idempotent on re-delivery
- The `/health` endpoint is unauthenticated and returns no sensitive data — safe to expose publicly

# ADR-0003: MCP Server as the Org Control Plane

**Status:** Accepted  
**Date:** 2026-03-08  
**Author:** ry-ops

---

## Context

The individual `git-fabric` app repos (unifi, proxmox, k8s, sandfly, etc.) each expose MCP tools for their own infrastructure domains. There is no tool surface for the **org layer itself** — managing repos, reading security overviews, auditing access, and querying the audit log.

## Decision

`fabric-ctrl` exposes a **stdio MCP server** that wraps the GitHub App's Octokit client as org-level tools. Tool names are namespaced with `org__` to distinguish them from infrastructure-domain tools.

The MCP server does **not** proxy the individual fabric app servers. Each fabric app's MCP server is responsible for its own domain. `fabric-ctrl` owns only the org/GitHub layer. This preserves the "one app, one domain" principle from the `git-fabric` architecture.

Consumers (Claude Desktop, git-steer, cortex) can load `fabric-ctrl`'s MCP server alongside individual app servers to get full coverage — org control plane + infrastructure domains — without any single server becoming a monolith.

## Consequences

- Tool surface is intentionally narrow — org operations only
- Adding a new org-level capability means adding a tool to `src/mcp/tools/org.ts` (or a new file in `tools/`)
- The MCP server shares the same App auth as the webhook server — one identity, two entrypoints
- No credentials are accepted as tool inputs — all auth is derived from the App identity at runtime

# ADR-0004: Zero-Trust Security Posture

**Status:** Accepted  
**Date:** 2026-03-08  
**Author:** ry-ops

---

## Context

The `git-fabric` org hosts infrastructure automation tooling. A compromise of any repo in the org is a potential pivot to real infrastructure (Proxmox, UniFi, k3s clusters, Cloudflare DNS). The security posture of `fabric-ctrl` must reflect this blast radius.

## Decision

`fabric-ctrl` adopts an explicit **zero-trust** posture across all surfaces:

### Never trust, always verify
- Every inbound webhook is HMAC-verified before dispatch — no exceptions
- Timing-safe comparison for all signature checks (prevents timing attacks)
- The `/health` endpoint is the only unauthenticated surface and returns no sensitive data

### Assume breach
- Secret scanning alerts are treated as **confirmed compromises** the moment they fire — rotation is the immediate response, investigation comes second
- Direct pushes to `main` are flagged regardless of who made them
- Auto-dismissed Dependabot alerts are logged to the audit trail — dismissal is never silent
- Workflows triggered from forks are flagged as potential exfiltration vectors

### Least privilege
- The GitHub App declares the minimum permissions required in `ADR-0001`
- Installation tokens are short-lived and never stored
- The private key never leaves the local machine — it is never committed, never logged, never transmitted

### Audit everything
- All access grants, org membership changes, and permission escalations are logged
- Audit log entries are retained for a configurable period (`AUDIT_LOG_RETENTION_DAYS`)
- The audit log is append-only from `fabric-ctrl`'s perspective — it does not modify or delete entries

### Sensitive path alerting
Changes to `.github/workflows`, `mcp.json`, `.env`, and `secrets/` in any org repo trigger elevated scrutiny — these are the paths through which supply chain attacks enter.
